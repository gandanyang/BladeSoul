# 08 · 顶层设计评审（制作人视角）

> 评审对象：01~07 全部设计文档 + 已落地的代码与数据资产。
> 评审时间：2026-09-12。评审人：制作人 / 顶层设计。
> 读者：所有参与本项目的 agent 与项目主人。
>
> 本文档只回答三件事：**什么是对的、什么是错的、现在该改什么。**
> 具体的任务派发见 [TASKS.md](TASKS.md)。

---

## 1. 总评

**这套顶层设计的水准明显高于同类个人项目。**

它不是"我要做一个只狼 like"这种愿望清单，而是一份**知道自己在赌什么**的设计：
赌注是"手感"，对冲手段是"每个机制都必须换来进攻机会"，止损点是"三条通关路径"。
01 文档给出的北极星——"我能感觉到**我自己**变强了，而不是我的角色升级了"——
是一句可以拿来做取舍判据的真北极星，这个项目里绝大多数决策都能回溯到它。

但目前它是一个**严重偏科**的项目：

> **设计成熟度 ≈ 8/10，可玩验证度 ≈ 0/10。**

7 篇文档、1 个被测透的裁决器、16 个数据资产，
而"人按下攻击键 → 屏幕上发生战斗"这件事，**一次都还没有发生过**。

对一个把"手感"当唯一 KPI 的项目，这是当前最大的、也是唯一的致命风险：
**手感不能被推理，只能被打出来。**

## 2. 做对了什么（附证据）

### 2.1 北极星可证伪 ✅
01 §1 不是"打击感要好"这种无法验收的话，而是给了三条可测指标
（首次弹开成功后 90% 的人会自发再试、手残玩家能通关、熟练玩家弹开率 50%+）。
**可测量的目标才是目标。**

### 2.2 "惩罚只惩罚效率，不惩罚存活" ✅
这是全套文档里最有价值的一句话（02 §1）。
它被落实成了具体机制：一闪按早 → 安全窗转格挡；防御键连打 → 只是弹不开、仍然格挡；
体干破裂 → 50 帧硬直但**不直接死**。
大多数"想做得友好"的项目只会加自动战斗，而这里给出的是一套**有代价的宽容**。

### 2.3 先写裁决器，不先写角色 ✅
02 §4 的六条规则被写成纯函数，59 个单测全绿。
顺序是对的：**先定义"谁赢"，再定义"谁怎么动"。**
反过来做，`if (isParrying && ...)` 会散落在动画回调、碰撞回调、AI 里，后期无法重构。

### 2.4 数值全部外置 ✅
针对 C# 无热重载这个真实风险，每个可变数值都进了 `.tres`。
这不是洁癖——06 §风险表把"调参吃掉工时"列为最大风险，而 04 §16 把
"改一行代码要重启游戏"列为工程第一坑。**两条风险被同一个对策解决了。**

### 2.5 一闪被正确地限制了 ✅
02 §2.3：一闪**不加资源成本**（否则变成资源管理游戏），
只用"22 帧不可取消后摇 + 落空 30 帧无防御 + 对 BOSS 只削体干"来定价。
对杂兵即死、对精英重削、对 BOSS 只给一个窗口——**分档正确，Boss 战才不会被一闪吃掉。**

### 2.6 IP 风险被主动识别 ✅
03 §3 明确分离了"历史公有领域（信长、第六天魔王、稻叶山城）"与
"Capcom 专有名词（幻魔、鬼之笼手）"，并给出替换方案（魔骸、噬魂笼手）。
**这一步 90% 的同类项目根本不会做，等收到律师函才做。**

### 2.7 教学 = 可以死的小场景 ✅
05 §5：每个机制一个专属场景、只教一个、提示只在失败 2 次后出现、
教学提示可关闭。这比"前 20 分钟不能死"的新手关高明得多——
**玩家在安全的场景里失败，比在不安全的场景里被保护，学得快得多。**

### 2.8 有止损点 ✅
06 明确说"做到 M5 就是一个完整可发布的作品，M7 可以随时砍掉"。
有止损点的计划才是计划。

## 3. 问题清单

按"会不会让项目失败"排序，不按"改起来费不费劲"排序。

### 🔴 P0-1：整个计划里没有一个"早到"的可玩验证点

**现象**：06 文档的里程碑顺序是 M0（骨架+裁决器+调试面板）→ M1（三连击）→ M2（弹开）。
也就是说，**前 5 周没有任何"能被人玩"的东西**。

**为什么是致命问题**：
01 §1 说得很清楚——这个项目的成败标准是"玩家第一次弹开后会不会自发再试一次"。
这是个**主观体验问题**，而主观体验无法通过读文档、写单测、做架构来验证。
更要命的是：如果 M2 结束时弹开手感不成立（06 自己也承认"不要往下走"），
那么 M0~M2 的 5 周里，有 4 周是在给一个可能不成立的核心下注。

**修订**：在 M1 之前插入 **M0.5「可玩闭环」**（见 §5）。
不要求好看、不要求动画、不要求敌人 AI——
只要求：**能走到木桩前，砍三刀，看到一个能被称为"手感"的反馈。**

### 🔴 P0-2：M7 的排期是假的，而它承载着"3.5~4 小时"的承诺

**现象**：

| 口径 | 内容 | 时长估计 |
|---|---|---|
| 06 §M7 | 第二~三章 + 终章 + 3 个 BOSS + 鬼力三元素 + 升级三线 + 道具 + 收集 + 挑战模式 + 2 个结局 | **5 周** |
| 07 §1.3 | 1.0 需要约 **220 个动作** | — |
| 03 §8 档位 2 | 3.5~4 小时流程 | — |

**为什么是问题**：
5 周内做出 3 个 BOSS + 2 个完整关卡 + 4 套系统，在"手感优先"的前提下是不可能的。
这不是"排期紧"，是"排期不存在"。而且它暴露了一个更根本的问题：
**README 从"2~3 小时"改成"3.5~4 小时"，并没有同步到任何排期或范围裁剪上**——
这正是 01 §8 和 06 风险表里自己警告过的 scope 膨胀。

**修订**（二选一，必须选一个）：
- **方案 A（推荐）**：**把 M5 垂直切片当作 1.0 的发布目标**，
  对外承诺改成"20 分钟到 1 小时的高密度动作 DEMO"，M6/M7 视反馈再谈。
  06 自己说过"做到 M5 就是一个完整作品"，只是没敢把这句话当决策用。
- 方案 B：保留 3.5~4 小时，但把总排期从 24 周改成 **40 周以上**，并承认 M7 是 12~16 周。
  同时按 07 的动作数量（220 个）重新估算，而不是按"章"估算。

### 🟠 P1-1：「资源流」（路径 C）与"不做复杂系统"自相矛盾

路径 C 是 01 §3 承诺的三条通关路径之一，它依赖：魂升级 + 鬼力三元素 + 消耗道具 + 快捷栏。
而这条路径的验收（05 §6"只用鬼力能磨过 BOSS"）在 06 里被放在 M6/M7——
也就是说，**我们在 M5 交付一个"承诺了三路径但只验证了两路径"的产品**。

**修订**：明确分档。
- M5 只承诺**路径 A（技巧）与路径 B（基础）**，并在 05/06/README 三处写死。
- 路径 C 标注为"1.0 才需要保证"，且它的系统在 M6 之前不投入任何工时。
- 顺带：01 §3 的表格要加一列"哪一档交付才需要它"，否则这份文档会一直诱导人去提前做。

### 🟠 P1-2："重试成本"没有进入系统设计，只活在检查清单里

05 §6 有一条硬标准："死亡到重开 ≤ 3 秒"，06 §M5 也写了"死亡 → 重开 ≤ 3 秒"。
但 04 的技术架构里**没有任何对应设计**：没有战斗重置、没有检查点重载、没有状态清理协议。
目前唯一的重开手段是调试面板的 F7（而且那个还没做）。

**为什么重要**：对手残玩家而言，"死一次要等 8 秒"比"BOSS 多 20% 血"更能劝退。
**重试成本是与弹开窗同级的难度参数**，不是 UX 细节。

**修订**：
- 把 `RetryToControlSeconds`（默认 3.0）写进 `DifficultyProfile`，与其他难度参数同级。
- 在 M1（不是 M5）就实现最小可用的"死亡 → 原地重开"，
  否则从 M2 开始每一次调参都在为"重试太慢"付利息。

### 🟠 P1-3：弹开窗有 4 个来源，但没有任何地方定义它们怎么合成

弹开窗最终值会被至少四处修改：

| 来源 | 文档位置 | 幅度 |
|---|---|---|
| 难度档基础值 | 02 §2.2 / 05 §2 | 6~16 帧 |
| 「技」线升级 | 03 §6.2 | +1 帧/级（未定上限） |
| DDA | 05 §3 | 最多 +4 帧 |
| 半自动防御 | 05 §4.1 | 由辅助系统判定 |

**为什么是问题**：三份文档各自说"改弹开窗"，代码里必然出现三处分别读 `DeflectWindowFrames`
然后又各自加一点，最终没有人知道这一帧到底从哪来——
**而弹开窗是本项目最重要的一个数字。**

**修订（技术红线）**：弹开窗只能有一个计算入口，且它是纯函数：

```csharp
// src/Combat/CombatTuning.cs —— 纯逻辑，可单测
public static int ResolveDeflectWindowFrames(
    int difficultyBaseFrames,   // DifficultyProfile.DeflectWindowFrames
    int upgradeBonusFrames,     // 「技」线，上限 +2
    int ddaBonusFrames)         // DDA，上限 +4
    => Math.Clamp(difficultyBaseFrames + upgradeBonusFrames + ddaBonusFrames, 4, 20);
```

**除这个函数外，任何地方不许直接读 `DeflectWindowFrames`。**
「半自动防御」不进这个公式：它改变的是"谁按下了防御键"，不是窗口宽度。

### 🟡 P2-1：飞行道具 / 远程敌人没有可执行的判定模型

02 §3 有"术法弹（可斩落）"，03 有弓兵与术士，05 有"术弹可被刀斩落"。
但 02 §4 的六条规则里没有任何一条描述飞行物被斩落。
这是一个真实存在的玩法缺口，且会在做敌人时才被发现。

**修订**：M5 之前**不做远程敌人**（在 02/03 里标注"1.0 之后"）。
如果将来要做，模型是明确的：飞行物持一个 `Hurtbox`，玩家的 `Hitbox` 命中它即销毁——
**不需要新规则，只需要不把它写成特例。** 现在只需要把"砍掉"这件事从 M5 范围里划出去。

### 🟡 P2-2：BOSS 的"多阶段"没有数据定义

03 与 06 大量依赖"P2 不断崖""阶段转换必须是已会机制"，但 04 里没有 `BossPhase` 概念。
如果阶段写成 `if (health < 0.5f)` 散布在 BOSS 脚本里，
那么 05 那条"P2 新增压力 ≤ P1 的 1.4 倍"的验收标准就无法执行。

**修订**：加 `BossPhaseProfile`（`[GlobalClass] Resource`）：
阶段阈值 / 招式池 / AI 参数覆盖 / 转场动画名。
**阶段是数据，不是代码分支。**

### 🟡 P2-3：音频被正确地排到了 P0，却被排在了 M2 的第 6 项

02 §6 和 07 §2 都说"音效是手感的 50%""M2 必须接上占位音频"。
但 06 §M2 的任务列表里，音效排第 6，验收标准里完全没有音频条目。

**修订**：
- "弹开音高递增"与弹开判定**同一天完成**，不进"以后加音效"的队列。
- M1 就要有挥砍/命中/脚步三种占位音效——**在灰盒阶段听到声音，比看到多边形更能判断手感。**

### 🟡 P2-4：性能预算内部有冲突，且没写优先级

07 §7 同时要求：1080p60 / 同屏 8 敌 / 体积雾 / TAA / 多个 `GPUParticles3D`。
在目标硬件未知的情况下，这几个目标会互相打架，而文档没说"掉帧时先砍谁"。

**修订**：写明降级顺序——
**先砍体积雾 → 再砍粒子数量 → 再砍同屏敌人数 → 最后才允许掉到 30fps。**
60fps 优先于画面（这条与"手感是唯一 KPI"一致）。

### 🟡 P2-5：文档之间已经出现过一次"同一件事两种写法"

已发生的实例：
- 02 §4 规则 3 写"双方都处于**攻击判定帧**"；
- 04 §6.2 的代码写 `def.IsAttackAction`（**在出招**，含前后摇）。

两者会导出不同的手感（砍一个挥空后摇的敌人是否算拼刀）。
已按 02 修正代码，并同步回 04。

**这不是偶发**：8 篇文档、多个作者、没有 owner 机制，就会持续发生。
**修订**：见 00 文档 §2（接口冻结）与 TASKS.md（任务看板）。
任何接口级改动，先改 00 文档，再改代码，最后改 04 的示例。

## 4. 三条"现在必须改"的修订（红线）

1. **插入 M0.5「可玩闭环」作为当前唯一目标。**
   在"能砍木桩并感觉到反馈"之前，不写任何新系统、不做任何新内容。
2. **明确 1.0 的发布目标是 M5 垂直切片。**
   在本轮派发任务时同步修订 06 与 README 的口径（方案 A）。
3. **弹开窗必须只有一个计算入口**（§3 P1-3 的 `CombatTuning`）。
   任何绕过它的写入一律视为 bug。

## 5. 修订后的里程碑（新口径）

| 里程碑 | 内容 | 验收（人话版） |
|---|---|---|
| ~~M0~~ | 骨架 + 裁决器 + 数据层 + 自检 | ✅ 已完成 |

## 6. 我作为顶层不亲自做的事

为了不让"顶层"变成瓶颈，以下工作一律派发给执行 agent，我只做评审与验收：

| 不亲自做 | 原因 |
|---|---|
| 写战斗管线、状态机、AI、面板、音频 | 有明确接口后是执行工作，不需要顶层判断 |
| 做关卡、写剧情文本、找素材 | 同上 |
| 调数值、调手感 | **必须由玩到它的人调**，不能由读文档的人调 |

我保留的三件事：
1. **接口冻结**（00 文档）——防止多头定义同一件事
2. **验收**——每条任务的验收标准由我确认，不通过就打回
3. **取舍**——范围、优先级、要不要砍的决策
