# 02 · 战斗系统设计

> 这份文档是项目的心脏。所有数值都是**基于 60fps 的整数帧**，
> 且**全部外置为 .tres 资源**（见 04 文档），本文档中的数字只是初版基准值。

---

## 0. 三条设计原则

1. **帧数据驱动**：一切以 60fps 整数帧为单位。不用秒、不用 delta 累加。
   `1 帧 = 16.67ms`。前摇 8 帧 = 133ms。
2. **单一裁决点**：所有命中/弹开/拼刀/一闪的判定，全部走同一个纯函数
   `CombatResolver.Resolve()`。绝不允许在 AI、动画、碰撞回调里散落 `if`。
3. **每个"成功"必须换来进攻机会**：防御不是挨打，防御是进攻的前置。
   如果某个防御动作只是"少掉点血"，它就没有存在价值。

## 1. 玩家状态机

### 状态清单

| 层 | 状态 | 说明 |
|---|---|---|
| 移动 | `IdleState` / `MoveState` / `SprintState` | 非战斗移动，带锁定目标时切侧向步 |
| 攻击 | `AttackState` | 轻斩三连（内部按 `ComboIndex` 分段） |
| 攻击 | `ChargedAttackState` | 蓄力斩，三段蓄力 |
| 攻击 | `ThrustState` | 突刺，高破防，可被敌人看破 |
| 防御 | `GuardState` | 持续格挡，内部记录"进入帧"以判定弹开窗 |
| 防御 | `DeflectState` | 弹开成功的 12 帧特殊状态，可派生**弹一闪** |
| 防御 | `GuardBreakState` | 体干破裂，50 帧大硬直，受伤 ×1.5 |
| 位移 | `DodgeState` | 前/后/侧闪避，无敌帧 8 帧 |
| 对峙 | `ClashState` | 拼刀，8 帧输入窗 |
| 处决 | `DeathblowExecuteState` | 忍杀演出，无敌 |
| 处决 | `DeathblowReceiveState` | 被忍杀 |
| 受击 | `HitLightState` / `HitHeavyState` / `KnockdownState` | 轻/重/倒地 |
| 生死 | `DeadState` / `ReviveState` | 死亡与复活（每条命一次） |
| 一闪 | `IssenState` | 一闪发动与结算，22 帧后摇 |
| 恢复 | `HealState` | 喝血：54 帧（0.9s），期间不能攻击；**受击不打断，但照样掉血**（见 §2.4） |

### 取消规则（手感的关键）

| 从 | 可被什么取消 | 从第几帧起 |
|---|---|---|
| 轻斩壹 | 轻斩贰 / 闪避 / 防御 | 后摇第 6 帧 |
| 轻斩贰 | 轻斩叁 / 闪避 / 防御 | 后摇第 7 帧 |
| 轻斩叁 | 闪避 / 防御 | 后摇第 12 帧 |
| 突刺 | 闪避 / 防御 | 后摇第 12 帧 |
| 蓄力斩 | 不可取消 | — |
| 一闪 | 不可取消 | — |
| 防御 | 任何动作 | 立即 |
| 闪避 | 攻击（避一闪窗）/ 防御 | 无敌帧结束后 |

**反连打机制（重要）**：
- 攻击后摇**不能**被"攻击键"取消 → 防止无脑连打，逼玩家看清节奏
- 但从任意动作**取消进入防御**后，有 **4 帧硬直**，此期间**无法弹开**
  → 这就是防"防御键连打"的手段。代价只是"这一下弹不开"，**仍然会格挡、不会挨打**
- 设计意图：**所有惩罚只惩罚效率，不惩罚存活**

#### 「安全窗」是本项目防劝退的核心设计

一闪按早了，**不算一闪，但也不会挨打**——会自动转成格挡姿态。

这意味着：
- 新手可以放心对敌人乱按攻击键，代价只是"打不出一闪"，而不是"被砍死"
- 熟练玩家会精确地去踩那 6 帧的完美窗
- **同一个按键、同一个动作，新手和老手的区别只是"效率"，不是"生死"**

这是整个难度设计里最重要的一条杠杆。

#### 一闪的代价（防止一闪过强让游戏退化）

- 一闪后摇 22 帧，且**不可取消**
- 一闪落空（敌人在窗口外）→ 玩家进入 30 帧"挥空硬直"，**此期间无防御**
- 一闪消耗 1 格**鬼力**？→ **不采用**。用资源限制一闪会变成"资源管理游戏"，
  我们采用**时间成本 + 风险成本**限制，不用资源成本

### 2.4 喝血（2026-09-12 新增，01 §0 规则 2 的直接落地）

**一个固定动作，不做药草、不做回血道具、不做菜单管理。** 按 `item_use` → 主角掏出酒壶喝一口。

#### 帧数据

| 段 | 帧数 | 说明 |
|---|---|---|
| 起手 | 10 | 掏壶，此段**可以被打断**（被打断则本次不消耗次数） |
| 饮用 | 34 | 进入此段后**受击不再打断**，但**伤害照常结算** |
| 收招 | 10 | 放回，此段可被闪避/防御取消 |

**取消规则必须写死，不许含糊**（T18 实施时暴露的歧义）：

| 段 | 能被谁打断 / 取消 |
|---|---|
| **起手 10 帧** | ✅ 可被受击打断（`StaggerState`）。**被打断则本次不消耗次数** |
| **饮用 34 帧** | ❌ **不接受任何打断**（包括受击），但**伤害照常结算** |
| **收招 10 帧** | ✅ 可被**防御 / 闪避**取消 |

> ⚠️ **饮用段也必须拒绝"防御 / 闪避取消"**——否则玩家按住防御键就永远喝不进去。
> "受击不打断"是这一段的设计目的（见下），不是实现疏漏。

#### 关键设计：受击不打断，但伤害不免疫

这是**为了避免《只狼》式的"背板喝血"**：

> 只狼的喝血逼玩家记住"BOSS 这一招之后才有安全窗口"——
> 那是**记忆惩罚**，与本作"让玩家理解规则、把规则玩漂亮"的方向相反。

所以这里改成：

- **喝血不会被打断**（进入饮用段之后）→ 玩家**永远能喝完**，不需要背招。
- **但来自身后的刀照常掉血** → 喝血的价值被抵消一部分。

于是博弈自然出现：**现在喝，还是再撑三秒？**
——而这个判断**只依赖"我面前有几个人、他们离我多近"**，不依赖背招。**这才是可读的博弈。**

#### 次数与补给（对齐 01 §0 规则 1/2）

| 项 | 值 |
|---|---|
| 每关基础次数 | **3~5 次**（宽松，不是稀有资源） |
| BOSS 战前 | **自动补满** |
| 死亡后 | **自动补满**，不永久消耗、不需要刷素材 |
| 与升级线的关系 | 「体」线可以提升次数上限与喝血速度（第 2 层"改变手感"） |

> **叙事接口（03 §2.7）**：药由同伴「绫」配。
> 于是"**BOSS 战前 / 死亡后自动补满**"这条规则**终于有了叙事解释**——
> 不是系统白送，是**有人给你把药补上了**。
> 零成本，而且顺手补掉了一个原本会被玩家问"凭什么"的漏洞。

### ★ 弹开与一闪的职责边界（2026-09-12 制作人裁定，参考《鬼武者》）

> **一闪可以应对一切攻击；弹开只能应对一般攻击。**

这不是平衡微调，是两条机制在**职责**上的分工：

| | 一般攻击（横斩 / 二连斩 / 重砸） | 「危」攻击（突刺 / 横扫 / 抓取） |
|---|---|---|
| **格挡** | ✓ 掉体干不掉血 | ✗（危·突刺除外：可格挡、但不可弹开） |
| **弹开** | **✓ 唯一的正面收益手段** | **✗ 一律无效** |
| **一闪** | ✓ | **✓ 有效**（含危·抓取——它没有别的反制手段） |
| **闪避 / 看破** | ✓ | ✓ 看破专治危·突刺 |

**为什么这样分**：弹开是"防守反击"，它该是**通用但低效**的手段；
一闪是"读招反杀"，它该是**万能但高风险**的手段。
如果弹开也能吃下危攻击，一闪就失去了唯一性——玩家没有理由去练那个 6 帧的窗口。

**这条裁定的三个连带后果（都必须落实）：**

1. **「危」的三种提示音从"可及性选项"升级为"机制必需"。**
   既然弹开对危完全无效，玩家判断错招式类型就会直接挨打。
   所以 07 §2.2 的高/中/低三音、以及屏幕上的图形符号，从"锦上添花"变成**硬需求**。
2. **危·抓取必须可被一闪**（原表是 ✗）。它是三者里唯一既不能弹、也不能看破的，
   如果连一闪都不吃，玩家就只剩"跑"这一种回答——那不是设计，那是惩罚。
3. **看破（危·突刺）的独特性被抬高了。** 它现在是危·突刺的招牌答案，
   教学顺序（05 §5：第一章教弹开 → 教看破）因此更清晰，不需要改。

**落到数据上的硬规则**（自检会强制检查，见 `src/Dev/SelfTest.cs`）：

- `Perilous = true` 的招式，`Parryable` **必须为 false**。
- 敌方招式默认 `IssenVulnerable = true`。

> 这条只约束**敌方**招式。玩家自己的蓄力斩 `Parryable = false` 说的是
> "敌人弹不开它"，与本节无关。

### 可读性铁律（AI 设计，不可违反）

1. 所有攻击前摇 **≥ 16 帧**（精英）/ ≥ 24 帧（杂兵），且必须有明确视觉起手
2. 前摇期间敌人**持续朝向玩家**，但转向速度有限（不允许零帧转身）
3. 同一敌人**不会在 8 帧内连续发动两个攻击**
4. 敌人连段结束后**必定有 ≥ 20 帧空隙**（给玩家反打，这是公平性的底线）
5. 「危」三类攻击用**不同音高**区分（高/中/低），让色盲玩家和听声辨位的玩家都能处理
6. **AI 不许读输入**：不能因为玩家按了攻击就取消自己的前摇；反应延迟 ≥ 8 帧
7. 敌人的攻击判定**必须可见**：刀光轨迹、地面预警圈、蓄气特效

## 4. 判定优先级（CombatResolver 规则）

同一 physics frame 内，当攻击方 A 的判定框与防御方 B 的受击框重叠，
**按下列顺序裁决，命中即返回，不再往下走**：

```
1. B 处于闪避无敌帧                              → MISS（完全无效）
2. B 有待释放的一闪 buff，且 A 处于可被一闪窗口   → ISSEN
3. A、B 双方都处于攻击判定帧                      → CLASH（拼刀）
4. B 处于弹开窗                                  → DEFLECT
5. B 处于格挡且夹角 ≤ ±70°                        → BLOCK
   （若 B 体干已满 → GUARD_BREAK）
6. 以上都不满足                                   → HIT
```

**这 6 行就是整个游戏的心脏。** 它必须写成不依赖场景树的纯函数，
可以被单元测试直接调用（见 04 文档 §14）。

### 一闪 buff 的统一实现（架构要点）

除「真一闪」外，其他一闪都走同一条路径：**获得 buff → 下一次攻击命中时升级为一闪**。

| 事件 | 授予的 buff |
|---|---|
| 弹开成功 | `IssenKind.Deflect`，持续 10 帧 |
| 完美闪避 | `IssenKind.Dodge`，持续 14 帧 |
| 拼刀胜利 | `IssenKind.Clash`，持续 8 帧 |
| 一闪命中 | `IssenKind.Chain`，持续 12 帧 |

只有「真一闪」需要特殊逻辑：**在按攻击的瞬间，扫描范围内敌人的
"距离命中还有几帧"**，若 ≤ 6 帧则记录 `IssenKind.Shin`。
即"输入时捕获意图，判定帧结算结果"。

这个设计让 5 种一闪共用一套结算代码，只有触发源不同。

## 5. 体干系统

- 玩家/敌人各有体干 `0 ~ MaxPosture`（玩家 100，精英 120，BOSS 200~300）
- 体干在停止受击后 `RegenDelay` 帧开始回复，速率 `RegenPerSecond`

### 关键规则：血量越低，体干恢复越慢（只狼式）

| 当前血量 | 体干恢复倍率 |
|---|---|
| > 70% | × 1.0 |
| 30% ~ 70% | × 0.6 |
| < 30% | × 0.3 |

**为什么需要这条规则**：
- 它让"先削血、再削体干"成为有效战术，而不是无脑弹开到底
- 它给"基础流"玩家（不敢弹开、只会闪避磨血）一条明确的推进路径
- 它让战斗有"越打越顺"的节奏感，而不是"从头弹到尾"

### 体干伤来源表

| 来源 | 对敌体干伤 |
|---|---|
| 弹开 | 18 |
| 拼刀胜利 | 25 |
| 看破（危·突刺） | 30 |
| 一闪（精英/BOSS） | 按 §2.3 的百分比 |
| 普攻命中 | 招式的 `PostureDamage` |
| **敌人攻击被格挡** | **0**（不给敌人涨体干） |

最后一条很重要：如果格挡也能削敌人态，玩家就会退化成"一直按防御"。

### 体干破裂

- 玩家破裂 → `GuardBreakState` 50 帧，期间受伤 ×1.5，**不直接死亡**
- 敌人破裂 → 头顶亮起**忍杀标记**，玩家按处决键发动忍杀
  - 杂兵：即死
  - 精英/BOSS：扣一格"命"（BOSS 有 2~3 格）

## 6. 拼刀细则

进入 `ClashState` 时：

1. 双方 HitStop **10 帧**，火花粒子，双方向后滑 **0.5m**
2. 镜头抖动 3 + 推近 0.2
3. 进入 **8 帧「拼刀输入窗」**
   - **玩家按攻击** → 玩家胜：敌人硬直 24 帧，敌体干 +25，玩家获得「拼刀一闪」buff
   - **玩家不按** → 平手：各自恢复，**敌人先动**（敌人相当于领先 6 帧）
4. **防挫败规则**：同一场战斗中，连续拼刀 3 次，第 3 次**自动判玩家胜**（即使没按）

第 4 条是刻意的：拼刀是"运气 + 反应"的混合，连续输拼刀最容易让人摔手柄。
给一个"最多连输 2 次"的隐性保险。

BOSS 的拼刀可以设计成**多次往返**（演出性）：双方互推 2~3 个回合，
最后一个回合玩家获胜。这比单纯拼一次帅得多。

## 7. 顿帧 / 慢镜 / 镜头 / 反馈

| 事件 | HitStop | 慢镜 | 镜头 | 粒子 | 音频 |
|---|---|---|---|---|---|
| 普攻命中 | 4 帧 | — | 抖 1 | 血花 | 切割声 |
| 被格挡 | 6 帧 | — | 抖 2 | 小火花 | 金属轻响 |
| **弹开** | 8 帧 | — | 抖 3 + 推近 0.15 | 白蓝火花 | 金属尖鸣（**音高随连击递增**） |
| **拼刀** | 10 帧 | — | 抖 4 + 推近 0.2 | 大颗粒火花 | 低频「锵」 |
| **一闪** | 14 帧 | 0.3s（×0.25） | 推近 0.4 + 侧移 | 黑白闪 + 血雾 | **静音 0.2s → 切割 → 低频轰鸣** |
| **忍杀** | 12 帧 | 0.5s | 环绕轨道 | 血柱 | 低频 + 心跳 |
| 体干破裂 | 10 帧 | 0.2s | 抖 5 | 破碎特效 | 骨裂脆响 |

### HitStop 实现（重要）

用**逐 actor 冻结**，**不要**用 `Engine.TimeScale`：

- `Engine.TimeScale` 是全局的，会拖慢 UI、音频、粒子，导致"整个游戏卡住"
- 逐 actor 冻结的效果是"世界静止，但火花与声音继续" → 这才是冲击感的来源

只有**一闪/忍杀的慢镜**才动 `Engine.TimeScale`，且必须用 Tween 平滑恢复
（`0.25 → 1.0` 用 0.3s 缓动），绝不能瞬间跳回。

### 弹开音高递增（细节但极重要）

连续弹开时，金属音的音高逐次升高（每次 +2 半音，最多 +12）。
玩家不用看 UI 就知道自己"连上了"，这是纯听觉的正反馈。
只狼的「叮叮叮叮」就是这么做的。

## 8. 输入缓冲与宽容机制（手残友好清单）

| 机制 | 参数 | 作用 |
|---|---|---|
| 输入缓冲 | 8 帧 | 后摇中预输入下一动作，避免"按了没反应" |
| 攻击链窗口 | 后摇前 60% | 让三连击容易打出 |
| 闪避缓冲 | 10 帧 | 连打闪避键不会空 |
| 尽地宽容（Coyote） | 4 帧 | 离开地面后仍可闪避 |
| ~~完美闪避宽容~~ | — | **已删除，见下方裁定** |

> #### ⚠️ 裁定：「完美闪避宽容」是一个**物理上不成立**的参数（2026-09-12 制作人）
>
> 原定义是"无敌帧结束后 3 帧内仍算完美闪避"。但：
> **无敌帧结束后就不再产生 `Miss`，而"完美闪避"只能由 `Miss` 触发。**
> 两者不能同时成立——这个参数要么永远不生效，要么等同于延长无敌帧。
>
> **闪避的"宽容"其实早就有了，而且是正确的那个**：
> **`DodgeBufferFrames`（输入缓冲，10 帧）**——它管的是"你在后摇里提前按了闪避也算数"。
> 那才是真正解决"手残玩家按不准"的参数。
>
> **结论**：删除 `PerfectDodgeGraceFrames`，**无敌帧严格等于 `DodgeIFrames`**。
> 理由与 08 §3 P1-3 同源：**一个数字只能有一个来源。**
> 留着它只会让后来的人误以为"宽容是它给的"，而实际起作用的是输入缓冲。
>
> 代码与 `.tres` 的清理见 `docs/TASKS.md` 的 **T21**；
> 在此之前 `DodgeStateTests.Grace_Frames_Do_Not_Extend_Invulnerability` 把当前语义钉着。
| **一闪安全窗** | 6 帧 | 按早了自动转格挡，**不挨打** |
| 连打防御惩罚 | `GuardCancelLockFrames`（4 帧） | 防连打，但只是"不能弹开"，**仍然格挡** |

#### ⚠️ 连打防御惩罚**必须**覆盖"中立态反复点按"（2026-09-12 制作人裁定）

原实现只在"从攻击/受击**取消**进入防御"时付这 4 帧硬直，
于是从**站立**反复点按防御时，每次进入都会重新开一次窗。

无头实测（T7 的弹开训练场景，机器人完全不看时机、每 4 帧松一下再按一下）：

```
[弹开训练] 交战 4 次：弹开 4 / 格挡 0 / 拼刀 0 / 挨打 0
```

也就是说：**连打防御可以零技术含量地弹掉一切。**
这与"弹开是本项目的立命之本"直接冲突——它会把这个机制退化成"连打就赢"。

**裁定（两版，第二版才成立）**：松开防御后 `GuardReentryLockFrames` 帧内**再次按下**，
**这一段防御直接不开窗**（`GuardEntrySource.QuickReentry`）——但**仍然格挡**，玩家不会因此挨打。

- 数值进 `DifficultyProfile`，与 `GuardCancelLockFrames` 同组，**不许写死在代码里**。
- 这**仍然只惩罚效率，不惩罚存活**：锁定期内照样格挡，玩家不会挨打。
- **四档难度都设成 8**——它不是难度旋钮，是**输入语义规则**：
  必须 ≤ 二连斩的重按间隔（约 9 帧），否则玩家连"接第二刀"都做不到。
  反连打的真正主力是**「危」攻击**（§3 裁定）。

#### ⚠️ 第一版修法是错的，这里是证据

第一版把快速重按判成 `Cancel`（**窗口晚开 4 帧**）。它看起来管用，
因为当时只测了"按 2 松 2"这一档。做节奏扫描之后才暴露：

| 连打节奏 | 第一版（晚开 4 帧） | 第二版（干脆不开窗） |
|---|---|---|
| 看时机按（对照） | 6/6 | **6/6** |
| 按住不放（对照） | 0/6 | 0/6 |
| 按 2 松 2 | 0/6 | 0/6 |
| **按 5 松 1** | **6/6** ❌ | **0/6** ✅ |
| **按 6 松 2** | **6/6** ❌ | — |
| **按 8 松 2** | **6/6** ❌ | — |
| 按 10 松 2 | 5/6 | — |

**根因**：窗口本身有 9 帧。"晚开 4 帧"只是把窗口往后挪——
只要一次按住 ≥5 帧（周期 ≤13 帧），前后两个窗口就**首尾相接**，等于永远开着。
而"按 5 松 1"≈ 每秒 10 次连打，是**正常人做得出来的动作**。
所以第一版等于没修。

**教训（写给以后的自己）**：
> **验证一个"防连打"机制，必须扫参数，不能只测一个点。**
> 一个只看单点的测试会让错误的修法显得完全正确。

**当前实测**（`DeflectTraining.tscn` vs `GuardSpam.tscn`，后者默认打最坏的"按 5 松 1"）：

| 机器人 | 弹开 | 格挡 | 挨打 |
|---|---|---|---|
| 看时机按（判定帧前 6 帧） | **4** | 0 | 0 |
| 连打（按 5 松 1） | **0** | 3 | 1 |

连打拿不到弹开收益，还会在"松手的那 1 帧"里挨打——
**这第二重代价是自然涌现的，不是人为加的惩罚**：冒进本身就会露破绽。
| 拼刀连败保险 | 3 次 | 连输 2 次后第 3 次自动赢 |

**设计意图总结成一句话**：
> 玩家永远不会因为手残而被打死，只会因为手残而打得慢。

这是本项目"足够有挑战性但不劝退"的技术保证。所有宽容机制加起来，
让"基础流"成为一条真实可行、不需要任何精准操作的通关路径。

## 10. 敌人 AI 设计原则

- 用**分层状态机**（`Idle → Approach → Circle → Windup → Attack → Recover → Retreat`），
  不用 GOAP/行为树复杂规划——**可预测性 > 智能**
- 敌人必须有**节奏**：进攻 → 观察 → 进攻，而不是无脑贴脸
- 每个敌人类型有 1 个"招牌机制"，教玩家一件事：
  | 敌人 | 教的机制 |
  |---|---|
  | 魔骸足轻（刀） | 基础弹开 |
  | 魔骸枪兵 | 看破（危·突刺） |
  | 魔骸弓兵 | 走位与距离管理 |
  | 魔骸巨汉 | 不可弹的攻击 → 必须闪避 |
  | 魔骸术士 | 优先击杀威胁目标 |
  | 精英·魔骸武士 | 二连斩 + 危攻击混合 |
- **Gank 规则**：同屏多个敌人时，**最多只有 2 个同时进攻**，
  其余保持"游走/威慑"状态。这是防止"被围殴到无法操作"的关键
- 敌人之间不互相伤害，但会互相"让位"（不重叠站位）
