## 2. 每一步的要点

### 2.1 参考图（第 1 步）

按 **12 §6 的六条技术规格**出图：浅色背景 / 无投影 / 不要薄片阵笠 /
武器不要伸出画面 / 轮廓光 / 1024×1536。

> **单图也能出 3D**（本次就是用单张 `ref_enemy_ashigaru_v2_d.png` 出的），
> 但四视图更稳。单图出的模型背面是"猜"的，**背面要用的资产必须走四视图**。

### 2.2 生成（第 2 步）

| 项 | 值 |
|---|---|
| 权重 | `F:\ComfyUI-aki-v3\ComfyUI\models\checkpoints\hunyuan_3d_v2.1.safetensors`（**7.37 GB**） |
| 输出 | `F:\ComfyUI-aki-v3\ComfyUI\output\3d\<名字>_00001_.glb` |
| 关键节点 | `VoxelToMesh ['surface net', 0.6]`、`VAEDecodeHunyuan3D [8000, 256]`（**256 ＝ octree 分辨率**） |

**★ 与 T35 卡不符的一处（已在 12 登记）**：卡里写的是从 `Tencent/Hunyuan3D-2`
下三个权重，实际**这 7.37 GB 的 checkpoint 自带 VAE**，`clip_vision/` 全程没用上。
照着卡下会拿到 404（那两个 URL 是错的）。

### 2.3 体检（第 3 步，**必做**）

```powershell
python tools\preview_glb.py <模型.glb> --out <输出.png> --min-faces 500
```

- **`--size` 上限 660**：三视图并排 ＝ 3×660 ＝ 1980px ≤ 2048（见 §4）
- **`--min-faces 500`**：只渲染主体。不加这个，21 万块碎渣会把图糊成一团毛刺，
  **看不出主体其实是好的**——本项目就在这里误判过一次"模型是平的"

### 2.4 ★ 去碎渣 ＋ 降面（第 4 步）

```powershell
python tools\cleanup_mesh.py <输入.glb> --out assets\models\<名字>.glb --faces 11500
```

实测：`660,136 面 / 214,826 个连通块` → 最大块 `175,278 面` → 降面到 **11,500 面**，
包围盒从被碎渣撑大的 `1.962 × 1.963` 收敛成人形 `1.355 × 1.700 × 0.457`。

> ⚠️ **必须先清理再降面**。直接对 660k 面降面会在 **81,016 面就降不动**——
> 21 万个碎块每块都要保住最少面数。这个坑已经踩过（见 `cleanup_mesh.py` 文件头）。

#### ★★ 还有一条被漏掉的：**产物没有法线，引擎里根本没法着色**

Hunyuan3D 的 `SaveGLB` **只写 `POSITION`**。把 glb 的 JSON chunk 打开看就一目了然：

```
enemy primitives: [['POSITION']]          ← 没有 NORMAL / TEXCOORD / COLOR_0
player primitives: [['JOINTS_0','NORMAL','POSITION','TEXCOORD_0','WEIGHTS_0']]
```

后果不是"不好看"，是**没有明暗**：Godot 导入后顶点格式里没有 `FormatNormal`，
整只魔骸渲染成**一块纯白**（T35 验收 2 的同屏截图第一版就是这么翻车的）。

而 trimesh 的 glb 导出是 `include_normals=None`——**只在缓存里已有法线时才写**，
所以"清理 ＋ 导出"这一步不会自动补上。`cleanup_mesh.py` 现在会显式
`fix_normals()` ＋ 触发 `vertex_normals` 并 `include_normals=True`。

> **别信"看起来有顶点色"。** 早先体检时 trimesh 报出 `vertex_colors` 均值
> `[102,102,102]`，一度被当成"模型有顶点色"——那其实是 **trimesh 的默认占位色
> `DEFAULT_COLOR`**，文件里根本没有 `COLOR_0`。**判颜色要看 glb 的 JSON chunk，不要看 trimesh。**

### 2.5 进 Godot（第 5 步）

```powershell
godot --headless --path . --import        # 新资产必须有 .import，否则 ResourceLoader 找不到
powershell -NoProfile -File tools\check.ps1
```

## 3. 已知坑

| 坑 | 现象 | 对策 |
|---|---|---|
| **生成物被碎渣撑爆** | 包围盒 1.96×1.96、看着"模型是平的" | `--min-faces` 看主体；`cleanup_mesh.py` 去渣 |
| **先降面会卡住** | 降到 81,016 面降不下去 | **先清理，再降面** |
| **产物只有 `POSITION`** | 没有 NORMAL / UV / 顶点色 / 材质 | ①**法线已由 `cleanup_mesh.py` 强制补上**；②颜色须等 **T27 补 UV ＋ 贴图**——在那之前它在引擎里就是白模 |
| **权重文件是坏的** | `vae\hunyuan3d_v2_vae.safetensors` 只有 15 字节，内容是 `Entry not found` | 下载失败把错误正文写进了文件。**已改名为 `.BAD-15bytes`**，免得被 ComfyUI 当成模型加载 |
| ★ **头被切掉了**（2026-09-13 实测） | 生成的模型**没有头**，顶部只剩领口残桩；换背面图重跑**一样没有** | 工作流里 `CLIPVisionEncode` 的 `crop` 默认是 **`center`**：参考图是 1024×1536 **竖图**，居中等比裁方形会把上下各切掉约 17%%，**头正好在上端**。改成 `crop = none` 后头部正常出现（顶部逐层半宽 0.486→0.130，单调收窄＝肩到头的正确锥度）｜**判据**：别只看"像不像人"，量顶部 5%% 的半宽——头约 0.13，肩约 0.35，量出来是 0.3+ 就是没头 |
| ★ **提示词挡不住"地面阴影"**（2026-09-14 实测） | 提示词写了两遍"没有地面、没有墙壁、没有影子、没有任何投影"，**六张图全都带上了地面接触阴影**。12 §6 第 2 条是本管线唯一**不能靠提示词保证**的一条 | 出图后必须**核验底色是否纯**（右下角取一块看是不是纯色）。本次按足兵 v2 的先例继续走，结果**没有**生成底盘（最大连通块是人形），但这是运气不是保证 |
| ★ **顶点色写成了 sRGB，引擎当线性读** | 上色后"黑 + 血红"在游戏里显示成"灰 + 粉红"（`#7A1418` → `#B84D54`）。看起来像美术风格问题，**不像 bug**，所以上线后一直没被发现 | `COLOR_0` 是**线性**通道。`paint_mesh.py` 已默认把调色板 sRGB→线性转换，并**回读自检**（正确时差 ≤2 级，选错时差 62 级）。判据：截图里采样血红区，修前 ≈ (185,92,100)，修后 ≈ (130,46,47) |
| ★ **上色会把补好的 `NORMAL` 又丢掉**（2026-09-14 实测） | 魔骸在引擎里**没有形体明暗**：胴甲、肩甲、草摺、佩楯糊成一块平色，**看不出身上有甲片**。与"没有法线"那条同源，但因为 Godot 会兜底生成法线，**渲染看起来是正常的**，所以藏了很久 | `cleanup_mesh.py` 补过法线，但 `paint_mesh.py` 的 `mesh.export()` 用的是 trimesh 默认 `include_normals=None`——**只在 `vertex_normals` 缓存里已有法线时才写**，而 `load()` 进来的法线不进缓存 → 一导出就丢。修法：导出前 `_ = mesh.vertex_normals` 并显式 `include_normals=True`，**并加读回自检**。判据（读 glb 的 JSON chunk，不要看观感）：修前 `['COLOR_0','POSITION']`，修后 `['COLOR_0','NORMAL','POSITION']`｜⚠️ **不要用 `fix_normals()` 来修**：生成式产物不水密，它靠闭合体积判内外，会翻掉一整片朝向 |

## 4. ⚠️ 两条与 Codex 本身有关的硬规则（**2026-09-13 连续打死两个会话**）

上一轮的会话不是被 Hunyuan3D 打断的，是被**请求组装**打断的。触发要三个条件同时成立：

1. 同一轮里有**并行工具调用**；
2. 其中一个返回**图片**，且该图**长边 > 2048px**（Codex 会插入 `<image_resize_notice>`）；
3. 该提示被插在图片输出**紧后面**——当图片不是本轮最后一条输出时，它把
   `call → output` 的配对**劈开**了。provider 用 `wire_api = "responses"`，强校验配对 → **整轮被拒**。

症状是那句看起来毫不相干的报错：

```
invalid_request_error: No tool output found for tool call call_01_...
```

**而且它会永久卡死那个会话**——历史里那条错位的提示每次重放都会被拒，
所以后续每轮都在 3 秒内失败，模型根本没机会跑。

**防复发（两条硬规则）**：

1. **`view_image` 不与其他工具调用放在同一轮**——看图就单独一轮。
2. **预览图长边 ≤ 2048px**（`preview_glb.py` 默认 `--size 660` 就是为此）。

> 现场快照与当时的恢复过程见 [HANDOFF-T35.md](HANDOFF-T35.md)。

## 5. 实测结果（T35 验收 2 / 3）

### 5.1 显存峰值与单次耗时（RTX 4060 Ti 16GB）

用 `nvidia-smi` 每秒采样，跑的是**同一份工作流**（`ashigaru_v2_d.png` → 那个 7.4GB 的 checkpoint）：

| 时刻 | 显存占用 |
|---|---|
| 清空模型前（ComfyUI 还压着 Z-Image） | 7.6 GB |
| **`free_memory` 之后（本机真实基线）** | **1.25 GB** |
| 权重加载中 | 1.8 → 4.2 → 5.9 → 7.6 GB |
| **峰值（KSampler/VAE 阶段）** | **9.31 GB** |
| 跑完（模型仍驻留） | 8.2 GB |

**结论**：单次生成的**净增约 7.9 GB**。16 GB 的卡装得下，还剩约 7 GB 余量；
但**它和 Z-Image 之类的常驻模型不能同时压着**——跑 3D 前先 `free_memory`。

| 项 | 实测 |
|---|---|
| **提交 → glb 落盘** | **77 秒**（冷启动，含 7.4 GB 权重加载） |
| 输出 | `output/3d/ashigaru_v2d_00002_.glb` |

> 77 秒是**冷**时间（先 `free_memory` 了）。权重驻留时应该更快，但**没有测**——
> 报告里不要把它当成重复生成的成本。

### 5.2 同屏辨识（验收 2）

```powershell
godot --path . res://scenes/tests/ModelShowcase.tscn     # 必须带窗口，--headless 是 dummy 渲染器
```

产物：[`assets/references/t35_model_showcase.png`](../assets/references/t35_model_showcase.png)（1280×720，Forward+/Vulkan）。

**结论：剪影辨识成立**——左边主角直立、双手自然下垂、有完整衣物与草鞋；
右边魔骸佝偻、手臂过长、下颌脱垂、指头残缺。10 §1 的"一眼分得清谁是人"**在剪影层面成立**。

**但配色那一半判不了**：魔骸还没有 UV/贴图，在引擎里是白模，
所以"黑+血红 vs 褪色蓝灰"这条**必须等 T27 补完贴图再验**。

> 两个为出这张图必须做的修正（都在 `ModelShowcase.cs` 里）：
> 1. **归一化身高**：主角模型只有 `0.998m`，魔骸 `1.700m`——
>    不归一化，这张图验的是"谁高"而不是"谁是人"。
> 2. **朝向**：主角模型的正面不是 `-Z`（要转 90° 才是正面朝相机）。

## 6. 怎么把本地通道拉起来（2026-09-14 实测，agent 视角）

平时靠**绘世启动器**点开；agent 要的是"不随命令结束被杀"，所以：

| 步 | 做什么 | 注意 |
|---|---|---|
| 1 | `F:\ComfyUI-aki-v3\python\python.exe F:\ComfyUI-aki-v3\ComfyUI\main.py --port 8188` | 必须放在**受管后台任务**里跑（不能用 `nohup ... &`：命令一结束子进程就被收走，日志停在 `Prestartup times` 而端口一直不通）。冷启动约 90 秒 |
| 2 | `curl --noproxy '*' http://127.0.0.1:8188/system_stats` | ⚠️ **`--noproxy '*'` 不能省**：本机配了 7897 代理，curl 会把本地请求也走代理，回一句"目标计算机积极拒绝"——**看起来像服务没起来，其实是代理** |
| 3 | 清显存（comfy `free_memory`） | Z-Image 之类常驻模型会挤爆 3D 生成（§5.1：峰值 9.31 GB） |
| 4 | 提交：拿 `tools/comfy_hunyuan3d_2.1_api.json`，改 `LoadImage.image` / `KSampler.seed` / `SaveGLB.filename_prefix`，`crop` **保持 `none`** | 输入图要**先复制进 `F:\ComfyUI-aki-v3\ComfyUI\input\`**，`LoadImage` 只认那里 |
| 5 | 产物在 `F:\ComfyUI-aki-v3\ComfyUI\output\3d\<prefix>_00001_.glb` | 单次冷跑约 75 秒 |

**跑 `tools/*.py` 用哪个 python**：这些脚本要 `trimesh` / `matplotlib`，
本机**只有 ComfyUI 自带那个装了**（managed python 与系统 Python310 都没有）：

```powershell
& 'F:\ComfyUI-aki-v3\python\python.exe' tools\cleanup_mesh.py ...
```

传路径要用 `F:/...` 的 Windows 写法——Git Bash 的 `/f/...` 会被 Python 当成一个不存在的字符串。

> **单图 vs 多视图**：`tools/comfy_hunyuan3d_2.1_api.json` 是**单图**结构
> （一个 `LoadImage` + 一个 `CLIPVisionEncode`），**吃不了多视图**。
> 所以"背面是编的"这件事在这个通道里**无法靠换输入图解决**（12 §6 说"四视图更稳"，
> 那需要换 MV 权重）。目前的降级办法是**让提示词里背面没有可编的东西**。

## 7. 什么时候**不该**走生成式通道：程序化道具（2026-09-14）

本文上面 6 节讲的全是"怎么把生成式通道跑通"。但有一类资产**根本不该进这条通道**——
**人造的、几何规则的**东西：笠、刀、枪、甲片、建筑构件。

T27 交付物里的「阵笠 + 打刀」就是这一类（T39 当时的建议正是"先只生成人，
笠与刀单独生成——每件都简单，而且独立部件更容易复用"）。它们改走
**[`tools/gen_props.py`](../tools/gen_props.py) 程序化生成**，理由是
**生成式通道在这两件上的已知失败模式全都存在**：

| 已记录的失败模式 | 记在哪 | 程序化为什么能绕过 |
|---|---|---|
| **薄片/悬空结构会被做坏** | TASKS.md T39：「阵笠是最容易被 clean topology 做坏的（retopo 常把薄片糊成一块或穿洞）」 | 车削一个**闭合的、有厚度的壳**——"薄片"在构造上不存在 |
| **细长结构伸出画面 → 深度估计失准、形状散掉** | 12 §6 第 4 条（打刀正是细长物） | 长宽厚按参数给定，不经过深度估计 |
| **产物没有 `NORMAL` → 引擎渲染成纯白块** | 本文 §2.4 | 导出前显式 `fix_normals()` ＋ 触发 `vertex_normals` 缓存并 `include_normals=True` |
| **必须先清碎渣再降面，否则降不动** | 本文 §2.4 | 面数按参数生成，**没有碎渣可去** |

**产出**：阵笠 `616` 面 / 打刀 `864` 面，都是**水密**网格（生成式产物从来不水密）。

### 7.1 ★ 把"该摆在哪"变成一个**算得出来的数**

```powershell
& 'F:\ComfyUI-aki-v3\python\python.exe' tools\gen_props.py --what jingasa `
      --fit assets\models\ashigaru_v2d_clean.glb
```

从 y=0.40 往上每 0.5mm 扫一次，找**第一个不与本体穿模**的笠缘平面高度
（判据 `contains`＝点在实体内，所以**要求外壳水密**；不水密直接报错，不给假数字）。
实测落点 `y = 0.7660`，并自带**对照组**：

| 项 | 值 | 说明 |
|---|---|---|
| 接触距离 | 0.24mm | ≈0 → 落点是真的"搭住"，不是浮空 |
| 再压低 2mm | 4 处穿模 | 边界是真的；**这一项若为 0 就说明判据在扫空气，落点不算数** |

> 这个模式可以推广：**凡是要"贴到另一个已有资产上"的东西**（笠、刀挂点、甲片、
> 装饰件），都该像这样把位置解出来 + 带对照组，而不是在场景里拖到"看着差不多"。

### 7.2 两条**只有看图才发现**的返工（数值断言全绿）

| 返工 | 现象 | 根因 |
|---|---|---|
| 笠像**斗篷**，滑到肩膀上 | 罩住整颗头、与肩甲连成一片 | 常量叫 `JINGASA_CAVITY`，语义是"顶点比顶面**低**多少"，`H - 0.030` 算出来是**内腔深 20.5cm**——而足兵的"头"只有 0.21m 高。**名字起错会一直误导自己**，故改名为 `JINGASA_CAVITY_DEPTH` |
| 笠像**平碟子** | 圆顶感、不是锥 | 外轮廓控制点太凸。阵笠的笠缘是**微微外张下压**的，改成"直线锥 + 靠笠缘处略下垂" |

> 与 §3 那个"顶点色写成 sRGB"的坑同一类：**面数、包围盒、断言全绿，
> 也证明不了"看起来对不对"**。3D 资产必须**同屏看图验收**
> （`scenes/tests/ModelShowcase*.tscn`，且**必须带窗口**）。

### 7.3 边界（别把这条通道用错地方）

程序化**只适合人造的、几何规则**的东西。**有机形体（人、魔骸的躯干、布料、
皮肤、植物）仍然必须走生成式通道**——它们没有可参数化的构造。
不要因为 `gen_props.py` 好用就把它推广到人身上。

### 7.4 配色仍然只有一个来源

程序化产物**只出几何**，顶点色一律交给 `paint_mesh.py`（新增 `--style jingasa` /
`--style katana`）。这样**调色板与 sRGB→线性转换仍然只有一处定义**——
否则 §3 那个色彩空间的坑会在第二个文件里再长一遍。
